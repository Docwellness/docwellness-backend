## Context

See proposal.md - Why/What Changes. Two ingredient-quantity representations exist today and both need this feature:

- `Recipe.ingredients[]` (`models/Recipe.js`): `{name, quantity, unit, category, priceLevel, description, image, isScalable, foodItemId}` - the catalog-authoring shape. `isScalable` already exists here but is an unrelated concept (`utils/dietPlanReadDispatch.js`/`controllers/patient/dietController.js` use it to decide whether an ingredient participates in serving-multiplier scaling at *read* time, e.g. a fixed pinch of salt not scaling with servings count) - this proposal must not touch or overload it.
- `RecipeVersion.ingredients[]` (`models/RecipeVersion.js`): `{foodItemId, rawQuantity, unit, preparation}` - the resolved, immutable-per-version shape the Ingredient Editor actually reads and writes, via `services/recipeVersioningService.js`'s `createCustomVersion(originalVersionId, updatedIngredients, opts)`. That function's current contract: the caller submits a full `updatedIngredients` array (every ingredient's new quantity, already resolved to a `foodItemId`); the backend trusts it verbatim, computes `nutritionPerServing` from it via `computeNutritionFromIngredients`, and separately rescales the dish-level `components` ("Makes (on the plate)") by the ratio of new-to-old total calories. No per-ingredient relationship exists between ingredients today - this is the one thing this change adds.
- `resolveGramsForIngredient(foodItem, rawQuantity, unit)` (same file) already converts any ingredient's quantity to grams via `FoodItem.unitConversions` or (for `ml`) `.density`, returning `null` when it can't - already used by `computeNutritionFromIngredients` to sum nutrition across mixed-unit ingredients, and reused by this change to sum a multi-ingredient core group's weight the same way.

A single core ingredient (e.g. Chapati's Whole Wheat Flour) is not universal: a combo/mixed dish (Mixed Vegetable, Vegetable Korma) has several ingredients that are *all* portion-meaningful together (every vegetable in the mix), with no single one of them a valid sole anchor - the design below treats "core" as a group, sized ≥1, not a single ingredient.

`controllers/dietician/planItemController.js`'s `createCustomRecipeVersion` is the only caller of `createCustomVersion` from the dietician's manual Ingredient Editor Save action (`regenerateSteps: true`); `services/ingredientAutoBalanceService.js`'s calorie-target auto-balance is a separate, more-frequent caller that must keep behaving exactly as it does today (see Non-Goals).

## Goals / Non-Goals

**Goals:**
- At least one `core` ingredient designated per recipe (no upper bound - a combo dish's whole core-category group can all be core together), flowing from `Recipe` through `RecipeVersion` to every edit.
- `createCustomVersion` recomputes sub-ingredient quantities deterministically when the core group's total weight changes, without requiring a new request field or a shape change to what the Ingredient Editor already submits.
- Recipes with no core ingredient designated (everything authored before this change) keep behaving exactly as they do today - zero backfill required for the feature to ship safely.

**Non-Goals:**
- `services/ingredientAutoBalanceService.js`'s calorie-target auto-balance (uniform whole-recipe scaling to hit a target) is untouched - it has its own explicit "fast/deterministic/offline" design constraint already and is a different trigger (system-computed target, not a dietician editing one ingredient by hand).
- No bulk backfill of `role` onto the ~214 existing recipes' ingredients - see Migration Plan.
- No fix for the unrelated, separately-tracked bug where 123 of those 214 recipes are also missing `components` entirely (different root cause: several past import scripts never set it at all).
- No live-preview-as-you-type implementation - that's Flutter dietician-app work, out of this repo; this design only defines the backend contract that preview would call or mirror.

## Decisions

**Schema: `role: { type: String, enum: ['core', 'sub'], default: 'sub' }` on both `Recipe.ingredients[]` and `RecipeVersion.ingredients[]` - cardinality is "at least one `core`", not "exactly one".**
An enum of two values reads clearly at every call site (`ingredient.role === 'core'`) versus a boolean whose polarity has to be remembered (`isCore`/`isCoreIngredient`), and leaves room to add a third role later (e.g. `optional`) without another migration. Defaulting new ingredients to `sub` means a hand-written `Recipe.create({...})` call that doesn't think about this field at all still validates. The cardinality invariant is deliberately "≥1 core, unbounded above" rather than "exactly 1": a single-grain dish like Chapati naturally has one core ingredient, but a combo dish like Mixed Vegetable or Vegetable Korma has no single valid anchor - every vegetable in the mix is equally portion-meaningful, and forcing a pick would be arbitrary and wrong (a dietician resizing "the mix" by adding more peas shouldn't leave carrots frozen at their old, now-disproportionate amount). This invariant is enforced by application code (`createRecipe`/`updateRecipe`/`generateRecipeWithAI`'s output validation), not a Mongoose-level constraint, matching how this schema already enforces cross-field invariants elsewhere (e.g. `dietaryHabits`/`freeFrom` conflicts checked in `utils/dietaryConstraintValidator.js`, not in the schema itself).

**Core-ingredient selection heuristic: the entire highest-priority category present, not a single ingredient with a tiebreak - but only mechanically GUARANTEED on the two deterministic (non-model) paths.**
Priority order (highest to lowest): `Grain`, `Carbohydrate`, `Protein Rich`, `Legume` > `Dairy`, `Vegetable`, `Fruit`, `Nut/Seed` > `Spice`, `Oil/Fat`, `Sweetener`, `Herb`, `Sauce/Condiment`, `Other`. Every ingredient in the highest-priority category that has at least one ingredient present becomes core; everything else is sub. For Chapati (one `Carbohydrate` ingredient - Whole Wheat Flour) this naturally produces a single core ingredient; for Mixed Vegetable (four `Vegetable` ingredients, no higher-priority category present) it naturally produces all four as core together, with no special-casing needed - the "group" behavior falls directly out of "take the whole category," not a separate code path.

This heuristic is implemented as one shared, deterministic JS function and used in two different ways:
- **`generateRecipeWithAI`**: given only as *prompt guidance* (the model is instructed to output `role` directly per ingredient, using this priority order as its reasoning). Verified live against real generations: a single-category dish (Chapati) reliably gets exactly the expected single core ingredient, but a combo dish's exact split can reasonably diverge from a strict same-category grouping - e.g. a real "Mixed Vegetable Sabzi" generation marked Cauliflower/Carrot/Peas/**Potato** (a higher-priority Carbohydrate) core while leaving Tomato/Onion (same Vegetable category as the other three) `sub`, reflecting a defensible bulk-vs-flavor-base culinary judgment rather than the mechanical category-only split. This is accepted, not corrected - see the spec's "prompt guidance, not a mechanical guarantee" wording. The only thing mechanically enforced for AI-generated recipes is *at least one* `core` ingredient (next bullet).
- **The deterministic heuristic function** (no model involved) is the actual mechanical, always-exact version of this rule, used for exactly two cases where there's no model judgment to defer to: (1) correcting a generated response that comes back with zero `core` ingredients, and (2) `createRecipe`/`updateRecipe`'s default when a dietician's request doesn't mark any `role` at all. Both of these get the literal "whole highest-priority category, together" behavior with no exceptions.

This mirrors real recipes: the grain/starch/protein/vegetable-mix is almost always the portion-meaningful part a dietician actually adjusts; oil/spice/liquid is seasoning relative to it - while leaving room for the model's real-world judgment to differ from a purely mechanical category match when it has a good reason to (a flavor-base onion/tomato genuinely does track more like a seasoning than the dish's bulk in many recipes).

**Computation location: entirely inside `createCustomVersion`, comparing the core group's aggregate weight - no request-shape change.**
The Ingredient Editor's Save action already submits the *full* new ingredient list every time (`{foodItemId, rawQuantity, unit, preparation}` per ingredient, no `role`). `createCustomVersion` already loads `original` (the `RecipeVersion` being replaced) before doing anything else. The added logic:
1. From `original.ingredients`, collect every `role: core` entry and sum `resolveGramsForIngredient(foodItem, rawQuantity, unit)` across them → `previousCoreGrams`. If any core ingredient's grams can't be resolved, or there are no core ingredients at all, skip straight to pass-through (see the "inert" decision below).
2. From the submitted `updatedIngredients`, find the entries with the same `foodItemId`s as `original`'s core ingredients and sum their grams the same way → `newCoreGrams`. (Each core ingredient's own submitted quantity is never overwritten - only used to compute this total.)
3. If `newCoreGrams` differs from `previousCoreGrams` beyond floating-point noise, compute `ratio = newCoreGrams / previousCoreGrams`; for every `role: sub` ingredient in `original.ingredients`, overwrite its entry in `updatedIngredients` with `Math.round(previousSubQuantity * ratio * 100) / 100` in the same unit, before nutrition is computed.
4. If the ratio is ~1 (core group's total unchanged, however individual core ingredients moved), `updatedIngredients` passes through untouched for sub ingredients too - identical to today.

This keeps `POST .../create-custom-version`'s request/response shape completely unchanged (no new field for the client to learn), server-owned (matches this codebase's consistent "AI/computed output always gets a deterministic backend backstop" philosophy - e.g. `enforceFiniteIngredientQuantities`, `checkNutritionPlausibility`, the `components` calorie-ratio rescale this feature sits right next to), and correct in a single place regardless of which client calls it (mobile app today, any future client). The trade-off - a dietician cannot change the core group's total AND hand-tune a sub ingredient in the same Save - is accepted deliberately (see Risks).
*Alternative considered*: have the client explicitly flag "I changed these core ingredients" and send only that, letting the server fill in the rest. Rejected for now because it's a strictly larger request-shape change for no behavioral difference in the common case, and the aggregate-comparison approach already correctly handles the "client did its own live preview and submitted already-correct numbers" case (recompute is a no-op, same numbers) as well as the "dumb client that didn't preview anything" case (server corrects it regardless).
*Alternative considered for the aggregation itself*: scale each sub ingredient by the *average* of the individual core ingredients' own ratios, instead of the ratio of their summed weight. Rejected: it weights a core ingredient that went from 1g to 2g (100% individual change, tiny absolute mass) the same as one that went from 200g to 220g (10% change, most of the dish's actual bulk) - summed-weight ratio reflects what a sub ingredient (oil/salt/liquid) actually needs to track: total mass being cooked, not an unweighted average of percentage changes.

**Sub-ingredient direct edits remain a first-class, trusted path when the core group's total is unchanged.**
If the dietician's request leaves the core group's total weight equal to `original`'s (whether because nothing in the core group changed, or because changes within it net out), every submitted quantity - including sub ingredients - is trusted verbatim, exactly like today. This is what makes "reduce salt for a hypertensive patient" still possible: it's simply a save where the core total didn't change. That saved version then becomes the new `original` baseline the *next* edit's ratios are computed from (RecipeVersion's existing immutable-snapshot model already works this way for every field - nothing new is needed to make this fall out correctly).

**Legacy or weight-unresolvable recipes: feature is inert, not an error.**
`createCustomVersion` treats both "no ingredient has `role: core`" and "a core ingredient's weight can't be resolved to grams" as the same branch, behaviorally identical to "core group unchanged" - full pass-through, zero recomputation, zero validation error, zero difference from today's behavior. A recipe only gains the new behavior once it's re-saved through `createRecipe`/`updateRecipe` (which apply the heuristic default) or `generateRecipeWithAI` (new recipes only), and only for ingredients whose `FoodItem` has the unit-conversion data `resolveGramsForIngredient` needs. This is what makes shipping this change safe with zero backfill and no new failure mode for existing data.

**Manual authoring validation: default zero explicit `core` via the heuristic, never reject for zero or for many.**
If a dietician's `createRecipe`/`updateRecipe` request marks zero ingredients `role: core`, that's simply "didn't think about it" - default via the heuristic rather than blocking, so this requirement never becomes a chore the dietician has to satisfy on every save of an otherwise-unrelated field. Marking several ingredients `core` is now valid input, not an error (it's exactly the Mixed Vegetable case) - there is no "too many core" rejection at all.

## Risks / Trade-offs

- [A dietician cannot change the core group's total AND hand-override a sub ingredient's quantity in the same Save - the second edit gets silently recomputed away.] → Mitigation: this is a two-step workflow (save the core change, then edit the sub ingredient in a follow-up save) rather than a blocked one; document it in the Flutter app's Ingredient Editor copy/UX so it reads as expected behavior, not a bug. Revisit only if dieticians report this as a real friction point.
- [The AI-generated `role` split can diverge from a strict same-category grouping - **observed live**, not just hypothetical: a "Mixed Vegetable Sabzi" generation marked Potato (Carbohydrate) core alongside 3 of 5 Vegetable-category ingredients, leaving Tomato/Onion (same category as those 3) `sub`.] → Mitigation: accepted deliberately, not corrected - see the "prompt guidance, not a mechanical guarantee" decision above; the model's bulk-vs-flavor-base judgment is often dietetically reasonable even when it doesn't match a purely mechanical category split, and the manual authoring path always lets a dietician override the pick explicitly per-recipe regardless.
- [A core group spanning incompatible units where one ingredient's grams are resolvable and another's aren't (e.g. a `piece`-unit core ingredient whose `FoodItem` has no `unitConversions` entry) makes the group's total only partially computable.] → Mitigation: per the "weight-unresolvable" decision above, this is treated identically to "no core ingredient at all" - full pass-through, never a partial/wrong total. Ensuring core-category `FoodItem`s have real `unitConversions` data is a data-quality concern for the existing `FoodItem` catalog, not new complexity this feature introduces.
- [Existing recipes silently keep old behavior until re-saved, so the feature's actual coverage grows slowly and unevenly.] → Mitigation: this is the deliberate, safer alternative to a bulk migration script guessing every legacy recipe's core ingredient(s) wrong at scale; a follow-up backfill script (out of scope here, same category-priority heuristic) can be proposed separately once this ships and the heuristic's real-world accuracy is validated on new recipes first.
- [Floating-point drift across many chained core-triggered rescales (V1 → V2 → V3 ...) could accumulate rounding error in sub-ingredient quantities.] → Mitigation: round each recomputed sub-ingredient quantity the same way `components` rescaling already does (`Math.round(value * 100) / 100`) - bounded, cosmetic-only drift, consistent with existing precision elsewhere in this service.

## Migration Plan

1. Schema: add `role` to `Recipe.ingredients[]` and `RecipeVersion.ingredients[]` (additive, defaulted - no migration script required for existing documents to remain valid).
2. Ship `generateRecipeWithAI` prompt/schema changes and `createRecipe`/`updateRecipe` validation/defaulting - new and manually-re-saved recipes start carrying `role` immediately.
3. Ship `syncV1FromRecipe` carrying `role` onto new `RecipeVersion` V1s, and `createCustomVersion`'s recompute logic (inert for any version whose ingredients carry no `role: core`, per the Decisions above - safe to deploy without touching existing data).
4. No cutover step, no downtime, no rollback complexity beyond a normal code revert - every existing `RecipeVersion` simply continues through the pre-existing pass-through branch until its parent `Recipe` is next saved through an authoring path that assigns `role`.
